NEW IN THIS ROUND (7 features)
------------------------------------------------------------------------

1) ACCOUNT LOCKOUT (brute-force protection, per account)
   Where: packages/backend/src/models/UserModel.ts (failedLoginAttempts,
   lockoutUntil, MAX_FAILED_LOGIN_ATTEMPTS = 5, LOCKOUT_MS = 15 min) —
   enforced in UserModel.findByCredentials; login goes through it in
   packages/backend/src/services/AuthService.ts.
   What: 5 wrong passwords in a row lock the account for 15 minutes;
   even the correct password is rejected while locked. A successful
   login clears the counter. Complements the per-IP rate limiter.
   How to prove:
   - Live (API): POST /api/v1/auth/login with a wrong password 5x, then
     POST again with the CORRECT password -> 401 "Account temporarily
     locked — try again in 15 min" (verified live).
   - Test: npm test — "locks the account after repeated failed logins".

2) PASSWORD STRENGTH POLICY + COMMON-PASSWORD BLACKLIST
   Where: packages/backend/src/utils/passwordPolicy.ts
   (assertStrongPassword), called from AuthService.register,
   AuthService.resetPassword, AuthService.changePassword. Client-side
   zod mirrors it in RegisterPage/SettingsPage/ResetPasswordPage.
   What: minimum 12 chars (zod, enforced first), a blacklist of ~100
   of the most common passwords (incl. 12+ char variants like
   "passwordpassword"), rejections of passwords containing the
   username or the email local part, and single-repeated-character
   passwords.
   How to prove:
   - Live: register with password "passwordpassword" -> 422 "That
     password is too common" (verified live); register with a password
     containing your username -> 422.
   - Test: npm test — "rejects weak and user-derived passwords".

3) MFA RECOVERY CODES (one-time, hashed)
   Where: packages/backend/src/services/AuthService.ts (enableMfa
   generates 10 codes, stores SHA-256 hashes in UserModel
   mfaRecoveryCodes with select:false; verifyMfaChallenge redeems and
   burns a code). Frontend: packages/frontend/src/pages/SettingsPage.tsx
   (shows codes ONCE with copy button after enabling MFA).
   What: when you enable TOTP MFA you get 10 single-use recovery codes
   (shown only once). If you lose your authenticator app, any one code
   signs you in instead of a 6-digit TOTP. Each code works exactly once.
   How to prove:
   - Settings -> Two-factor authentication -> enable -> codes appear.
   - Test: npm test — "issues 10 recovery codes on MFA enable, and each
     code works exactly once" (second use is rejected 401).

4) ACTIVE SESSION MANAGEMENT + "SIGN OUT EVERYWHERE"
   Where: packages/backend/src/models/RefreshTokenModel.ts (device, ip,
   lastUsedAt on each refresh token), AuthService.listSessions /
   revokeSession / revokeOtherSessions; endpoints in
   packages/backend/src/routes/authRoutes.ts
   (GET /auth/sessions, DELETE /auth/sessions/:id,
   POST /auth/sessions/revoke-all). Frontend:
   packages/frontend/src/pages/SettingsPage.tsx (Active sessions card).
   What: every login records the device/browser + IP. Settings lists
   all active sessions with "this device" marking, lets you revoke any
   single session instantly, or sign out everywhere except the current
   device. Password changes/resets already revoke all sessions.
   How to prove:
   - Settings -> Active sessions: log in from two browsers, both
     appear; "Sign out everywhere else" keeps only the current one.
   - Test: npm test — "lists sessions and signs out everywhere else".

5) SECURITY ALERTS BY EMAIL (new-IP login, password changes, MFA toggles)
   Where: packages/backend/src/services/AuthService.ts
   (sendSecurityAlert + login's lastLoginIp tracking). Emails go through
   utils/email.ts — with real SMTP they are sent; without SMTP (dev)
   they are printed in the backend log as "[mail:dev] email would be
   sent" so you can see them.
   What: you get an alert when (a) your account is signed into from a
   NEW IP address, (b) your password is reset, (c) your password is
   changed, (d) MFA is enabled, (e) MFA is disabled — each logged in
   the Activity log as well.
   How to prove: log in from a new IP (or after changing your IP) and
   watch the backend log for the "New sign-in detected" alert; change
   your password in Settings and see the "Password changed" alert.

6) SENSITIVE-DATA REDACTION IN LOGS
   Where: packages/backend/src/utils/logger.ts (redact / redactDeep —
   applied to every console + file log line).
   What: any logged object key matching password/token/secret/api-key/
   cookie/authorization etc. is replaced with [REDACTED]; token values
   embedded in URLs (e.g. reset/verify links in dev mail bodies) are
   scrubbed too. Passwords and tokens never reach the logs.
   How to prove:
   - Live: POST /api/v1/auth/forgot-password, then grep the backend
     log — the reset link prints as "reset-password?token=[REDACTED]"
     (verified live).

7) IDLE SESSION TIMEOUT (auto sign-out)
   Where: packages/frontend/src/layouts/RootLayout.tsx (idle timer on
   mousemove/keydown/click/touch/scroll).
   What: after 25 minutes of no activity a warning banner appears;
   after 30 minutes the session is ended and you're taken to the login
   page. Any activity resets the timer.
   How to prove: log in, stop touching the machine for 30 minutes —
   a warning appears at 25 min and you're signed out at 30 min.

8) TOTP TWO-FACTOR AUTHENTICATION (MFA) FOR ALL ACCOUNTS

   What: QR-code setup (Google Authenticator/Authy), two-step login

   never exposed. Proof: Settings -> enable -> log out -> log in asks
   for a code.

   Where: AuthService (forgotPassword/resetPassword/changePassword),
   routes /auth/forgot-password, /auth/reset-password,
   /auth/change-password; pages /forgot-password, /reset-password,
   Settings -> Change password.
   What: one-time 1-hour reset links (hashed at rest, single use,
   revokes all sessions), change-password requires the current password
   and logs out other sessions. Proof: /forgot-password -> link (dev:
   backend log) -> reset -> old password rejected 401.

    What: verification link on registration; status + resend in
    Settings; seeded accounts pre-verified; .local admins auto-verified.
    Proof: register -> link in dev log -> /verify -> status updates.

    different emails and try cross-role actions.

    Where: packages/backend/src/middleware/auth.ts (protect,
